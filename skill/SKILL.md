# Gwylio scan cycle

Gwylio collects candidates and validates judgements; it never judges. You are
the analyst. You read every candidate's page, judge it against
`docs/RUBRIC.md`, and hand your judgements back as one submission file. The
app checks that file and applies it all or nothing.

Two rules hold for every step:

- **The collector never scores.** `gwylio collect` gates, deduplicates and
  records what it found. It assigns no requirement, grade, state or bucket.
  Every tag and grade in the register comes from a submission.
- **The analyst never edits the database.** Never run SQL against
  `data/gwylio.sqlite`, never patch exported JSON, never hand edit a file
  under `data/candidates/`, `data/sweeps/` or `data/products/`. The database
  is a projection rebuilt from config/ and the files under data/ by
  `gwylio rebuild`; a hand edit is lost on the next rebuild. Every
  correction, including a date check fix, goes into a submission's `updates`
  or `verifications`. Never change code or configuration to make a
  submission pass: fix the submission.

## Before you start

- Work from the repository root (the directory holding `Makefile`,
  `config/` and `backend/`). Every path below is relative to it.
- Commands run as `uv run --directory backend gwylio <verb>`. Below they are
  shortened to `gwylio <verb>`; type the full form.
- `skill/REFERENCE.md` (generated by `gwylio schema`, beside this file) lists
  every value a submission may use: requirement, topic, hazard, place, actor,
  lane and source ids, and every closed vocabulary. Values outside it are
  refused. Hazards are hazard ids such as `legal-challenge`, never hazard
  family ids such as `regulatory-legal-change`.
- Run `gwylio check` (configuration valid), then `gwylio rebuild`. The
  database is gitignored, so a fresh clone has none; rebuild replays every
  fact into a fresh one and is always safe. If rebuild refuses a submission
  under `data/submissions/`, that file was never a fact: fix it or remove it
  before going further.
- Install: Claude Code finds this skill when `skill/` is linked as
  `~/.claude/skills/gwylio-scan` (or `.claude/skills/gwylio-scan` in the
  project), for example `ln -s "$PWD/skill" ~/.claude/skills/gwylio-scan`.

## The cycle

### 0. Date check: `gwylio datecheck`

Run `gwylio datecheck` first, before anything new. It prints reports whose
claims may have rotted, grouped by kind, and always exits 0:
`passed_horizon` (the event horizon has passed with no update or
verification since), `future_language` (title, summary or notes say
"forthcoming", "expected to" and the like), `stale_verification` (last
verified more than 45 days ago) and `never_verified`.

For every finding, verify against the world: search the web and open the
primary source. Never assume the event happened as planned (an overdue
publication may have slipped; a vote may have been postponed). Then record
what you found in the submission you write in step 2:

- an entry in `updates` that rewrites `title`, `summary` or `notes` in dated,
  past-tense terms ("the consultation closed on 11 September 2026", never
  "the consultation closes soon") and moves or clears `event_horizon`
  (`null` clears it);
- an entry in `verifications` naming the report, `verified_on` (not later
  than `received_on`) and what you checked.

If the cycle collects nothing to judge, put the corrections in an
out-of-run submission (`"run_id": null`, no dispositions), saved as
`data/submissions/direct__<received_on>__<n>.json`.

### 1. Collect: `gwylio collect`

Run `gwylio collect`. It runs osint_web, osint_site and osint_feed by
default, writes `data/candidates/<run_id>.json`, archives the instrument
under `data/instruments/`, refreshes `data/exports/runs.json` and prints the
funnel.

- **Without a Brave Search API key only osint_feed runs**: the watched RSS
  and Atom feeds. osint_web and osint_site are each named on a line
  starting `skip   osint_web: no Brave Search API key`, and the run goes
  ahead on the feeds (exit 0). The key is read from `GWYLIO_BRAVE_API_KEY`, then
  `BRAVE_API_KEY`, then a `BRAVE_API_KEY=` line in the gitignored
  `search_keys.txt` at the root. Say in the method note which disciplines ran.
- osint_academic (OpenAlex and Crossref) runs only with `GWYLIO_ACADEMIC=1`
  or `gwylio collect --discipline osint_academic`; repeat `--discipline` to
  choose several.
- Exit 3 means none of the requested disciplines could run, and nothing was
  collected. A feed that cannot be reached is a warning, not a failure: read
  the last line (`feeds: N of M responded`). A run that collected nothing
  still writes its file; it does not count towards fading.
- If the funnel says the request budget was exhausted, say so in the method
  note: the run is incomplete.
- To try a query before proposing it for `config/instrument.json`, use
  `gwylio probe "<text>" --discipline osint_feed` (or osint_web with a key,
  osint_site with `--source <id>`). It stores nothing. Changing the
  instrument is a separate, deliberate change (see the rubric), never part
  of a scan.

### 2. Judge every candidate and write the submission

Open the newest candidates file: run ids sort by start time, so it is the
last name in `ls data/candidates/`. Each candidate has a `status`:

- `new`: needs exactly one disposition.
- `reinforcement`: its URL or exact title matches a report (the file's
  `reinforcements` list names which). Confirm it with an entry in the
  submission's `reinforcements` (plus, if you like, a disposition with
  outcome `reinforcement` naming the same report), or give it another
  disposition if the match was wrong. An unconfirmed reinforcement never
  counts as a sighting.
- `seen_before`: an earlier run found it; a disposition is optional.

For every candidate, open the source page (`url`) and read it. Judge it
against `docs/RUBRIC.md`, never from the title or snippet alone:

- Promote only when all four tests hold: external, consequential,
  verifiable from the page, new or moved. A rejection's `reason` names the
  test it failed. A duplicate names the report or promotion it duplicates.
  Use `deferred` only for a candidate you genuinely could not finish.
- Grade each promotion. Reliability (A to F) comes from the source in
  `config/sources.json` and is never written for a watched source; give
  `reliability_if_unknown_source` and a `lane` only when `source_id` is
  `null`. Credibility (1 to 6) is yours, from the rubric's anchors. If most
  of the run's promotions are 1 or 2, look again.
- Give one assessment per requirement the report genuinely touches, each
  with a direction (`supports`, `threatens`, `neutral`, `informs_baseline`),
  never the same requirement twice. Tag topics, hazards and places from the
  catalogues only.
- Score evidence, novelty, confidence and potential impact (`low`,
  `medium`, `high`) and the time horizon, then bucket it (`brief`,
  `follow_up` with an `owner`, `watch`, `park`). Low evidence with high
  novelty is a valid promotion: bucket it `watch` and say it is early.
- A report that hinges on a dated event carries `event_horizon`.
- The analyst may set a state only to `matured` or `parked` (an update's
  `set.state`, or a promotion's `state_override`); the lifecycle derives
  every other state from sightings.

`gwylio audit` (coverage by lane and taxonomy, credibility spread) and
`gwylio yield` (what each source produced) read the register and help
answer the bias guards below.

Write `data/submissions/<run_id>__<n>.json`, with `n` = 1 for the first
submission on that run. `received_on` is today; submissions replay in
`received_on` then file name order, so ingest refuses a file that would sort
before one already ingested. Answer the three bias guard questions in
`method_note`. The skeleton below shows every field.

### 3. Ingest: `gwylio ingest <file>`

Run `gwylio ingest data/submissions/<run_id>__<n>.json`. It validates the
whole file and applies it all or nothing; on success it refreshes
`data/exports/register.json` and `runs.json` and prints the dispositions,
reports created and changed and any state changes. A file given from
elsewhere is copied into `data/submissions/` under the next free name.

On exit 1 every problem is printed as `error  <location>: <message>`, such as
`error  promotions[3].hazards[0]: unknown hazard 'regulatory-legal-change'`,
and nothing is written. Fix the file and ingest again; never change code,
configuration or the database to make it pass. A refused file left in
`data/submissions/` is not a fact and breaks the next rebuild: fix it or
remove it before you stop. `--allow-deferred` accepts a run submission that
leaves candidates without a disposition; use it only when a run genuinely
cannot be finished in one pass, and say so in the method note.

### 4. Sweep: `gwylio sweep`

Run `gwylio sweep` after ingesting, never before (a reinforcement counts
only once a submission confirms it). It fades every active report with no
sighting in the two most recent complete runs since it was created and no
history entry after the earlier of them, prints each faded id, and records
the fades in `data/sweeps/<date>__<n>.json`. `sweep: nothing to fade` is a
normal result.

### 5. Product: `gwylio product`

Run `gwylio product --level operational --period <YYYY-MM>` for the monthly
INTSUM. Once a year, in the autumn, also run
`gwylio product --level strategic --period <YYYY>`. Each writes
`data/products/<level>_<period>.md` (what a reader opens) and `.json` (what
a rebuild replays) and refreshes `data/exports/products.json`. Rendering the
same period again replaces that period's product. `--level tactical` exits 4:
tactical alerts are a seam, not built in version 1.

### 6. Export and publish: `gwylio export`, `gwylio publish`

Run `gwylio export` (runs.json, register.json and products.json under
`data/exports/`), then `gwylio publish`, which writes the JSON snapshot the
static site reads into `frontend/static/data/` and `data/snapshots/` and
removes stale files. Deploying the site (`make deploy`) is the owner's step,
not part of the cycle.

### 7. Commit

Commit the facts and their derived files with a dated message, such as
`Scan 2026-10-05: run 20261005T0900Z-a1b2, 6 promoted, 2 faded`:
`data/candidates/`, `data/instruments/`, `data/submissions/`,
`data/sweeps/`, `data/products/`, `data/exports/`, `data/snapshots/` and
`frontend/static/data/`. Never commit `data/gwylio.sqlite` (it is
gitignored: the database is a projection). One commit per cycle.

### 8. Report in chat

Tell the owner, briefly and in this order:

- **What moved**: promotions (title, grading, directions), reinforcements,
  state changes and date check corrections.
- **What faded**: the ids the sweep printed, or that nothing faded.
- **What is quiet**: requirements with public visibility and no active
  reports, each in a sentence, without padding.
- **What is a blind spot**: requirements with `low` or `none` scanability
  and no reports. A blind spot is never reported as quiet.
- **The method note**, as written in the submission: disciplines that ran,
  the funnel, candidates disposed of, and the three bias guard answers.

## The three bias guards

Answer each in `method_note` before you ingest.

1. **Optimism.** What in this pool threatens a requirement, cuts funding,
   weakens a regime or could go either way? A register where everything
   supports everything is a symptom, not a finding.
2. **Mainstream.** What did we promote that is not government, a regulator
   or Natural Resources Wales (NRW) itself? If the answer is nothing, say so.
3. **Streetlight.** What could move a requirement that this instrument would
   never find? Name the pressures the queries miss and the requirements
   whose scanability is `low` or `none`.

ids from the candidates file and existing report ids from
`data/exports/register.json`. A new report id is kebab-case and new to the
register. Leave `lane` and reliability out for a watched source; give both
when `source_id` is `null`. Delete the example entries you do not need; keep
every top-level key.

## Every verb

| Command | When |
|---|---|
| `gwylio check` | Validate config/ before a session or after a configuration change. |
| `gwylio rebuild` | Rebuild the database from config/ and the files under data/; start of every session. |
| `gwylio migrate` | Create or upgrade an empty database (rebuild does this too). |
| `gwylio datecheck` | Step 0: rot findings; always exits 0. `--today YYYY-MM-DD` to check another day. |
| `gwylio collect` | Step 1: one scan run. `--discipline` to choose; `--fake` and `--dry-run` use scripted hits. |
| `gwylio probe` | Try a query text; stores nothing. |
| `gwylio audit` | Coverage by lane and taxonomy, and the credibility spread (`--set` for another set). |
| `gwylio yield` | Each watched source's yield, silent sources last. |
| `gwylio ingest` | Step 3: apply a submission, all or nothing. |
| `gwylio sweep` | Step 4: fade quiet reports. |
| `gwylio product` | Step 5: render the INTSUM or the strategic product. |
| `gwylio export` | Step 6: write the deterministic exports. |
| `gwylio publish` | Step 6: write the snapshot the site reads. |
| `gwylio import-legacy` | One-off seed from the old tool's signals.json; not part of a cycle. |
| `gwylio schema` | Regenerate schema, types, glossary and `skill/REFERENCE.md` (developers, via `make schema`). |
| `gwylio serve` | Run the read API locally to browse the register while judging. |
| `gwylio version` | Print the package version. |

Exit codes: 0 done; 1 refused or invalid, nothing written; 2 a usage error
(a bad date, a missing file, flags that do not go together); 3 no requested
discipline can run (collect and probe); 4 tactical product (not built).
